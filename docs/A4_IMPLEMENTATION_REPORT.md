## Thay đổi v1.1

API cold start cần Mongo/init nhưng không chờ Redis. Redis health recovery và optional producer chỉ bắt đầu sau Mongo/index/catalog init. Một recovery loop node-redis/client có backoff 100–1000ms, đóng/cancel khi shutdown. Worker cold start còn fail closed, cần supervised restart sau startup budget. Giữ live/full/probes cũ; thêm `/health/read-ready` alias fixture và sanitized `/health/capabilities` (ready/unavailable/disabled; worker=`unknown`, không suy running/reconcile từ ping). Compose API bỏ Redis health startup gate và dùng read health, full vẫn strict.

HTTP enqueue có tối đa 4 raw operations, caller deadline 1500ms, slot giữ đến settlement và AbortSignal chặn bước dispatch muộn. Producer offline queue tắt, command backlog tối đa 256 để đủ BullMQ bootstrap; reconciliation không chồng lấp, late results không làm ready lại. Transition logs có role/service/count và không heartbeat spam.

**Sửa lỗi actual Compose · 22/10/2026:** Mongo healthy và Docker DNS/TCP từ web đều đạt; disposable API image chạy `MongoClient.connect()` riêng cũng đạt. Entrypoint không secret đạt, nhưng bật producer khi hostname Redis chưa tồn tại làm Mongo connect timeout. Eager Redis lookups tranh tài nguyên DNS trước required Mongo startup; tăng startup attempts không giải quyết nguyên nhân. Sau khi dời Redis startup xuống sau required init, actual Compose regression đạt, không đổi readiness hoặc timeout. Test in sanitized container state/logs trước cleanup, kể cả container đã exit.

## Hạn chế và rollback

- **Giới hạn routing / load balancer production:** `compose.yaml` mặc định vẫn dùng `GET /health/ready` (full readiness) cho container `api`, và Vite dev server (`apps/web/vite.config.ts`) chỉ proxy `/api` (các đường dẫn `/health/*` gọi qua cổng Vite trả về SPA HTML shell `200 text/html`). Việc đọc fixture/Mongo qua direct HTTP và qua Vite `/api` proxy thật sống sót khi Redis sập tại local chứng minh hành vi của process API và Vite proxy, nhưng **không chứng minh** rằng load balancer hoặc ingress bên ngoài trong môi trường production sẽ tiếp tục định tuyến request tới instance đang trả `503` ở `/health/ready` nếu chưa cấu hình tách probe theo capability (`GET /health/ready/fixture`, `GET /health/ready/mongo`).
- **Trạng thái cổng và phạm vi:** Không còn blocker kỹ thuật trong phạm vi A4. Tuy nhiên, A4 chỉ giải quyết vòng đời dependency và recovery của hạ tầng hiện có; cổng quyền nguồn P2.1, P2.2 news ingestion, collector vàng thật P1.3B và mọi collector tự động vẫn đóng cho tới khi có phê duyệt riêng.
- **Kế hoạch rollback:** Nếu phát hiện hồi quy sau triển khai, rollback đồng bộ cặp code API và worker (`apps/api/src/*`) về baseline `eb3a6b2` (PR #38). Vì A4 không thay đổi schema MongoDB, không đổi định danh `deliveryId`/`payloadDigest`/`jobId`/tên job BullMQ và không thêm collection mới, việc rollback không cần data migration, không cần xóa queue hay xóa volume. Sau rollback, kiểm tra lại `GET /health/live`, `GET /health/ready` và luồng submit/replay fixture.
